OP Command Arguments Reference

Command-level argument behavior for /op-build, /op-simple-build, /op-resume, /op-initialize, and /op-plan.

Date: 2026-03-15 Source: scripts/op/opctl.py + scripts/op/op_core.py Runtime: OP Simple path

Command Semantics Snapshot

/op-build is the one-command entrypoint. Its default --start-policy auto resumes valid OP Simple state when possible; otherwise it starts a fresh run and runs /op-initialize first only when mission/scope is supplied, --override-old-plan is set, or required planning baseline artifacts are missing.
/op-resume requires .op-simple/current/initialize_state.json. If that marker is missing, resume is blocked.
Run-base note: --run-base-source-branch sets the source for a new run-base branch in fresh /op-build. It is treated as explicit fresh-run intent and does not invoke resume semantics.
/op-simple-build runs the OP Simple runtime directly (no initialize pre-step).
Cycle release note: watcher-based cycle release now runs by default; the old public --sleep-minutes switch has been removed.

Cross-Command Notes

  • /op-build default start behavior: if --start-policy is omitted, runtime uses auto and resumes only when existing OP Simple state and run-base branch are both valid.
  • /op-build default source branch: if --run-base-source-branch is omitted, runtime uses main as run-base source for fresh runs.
  • /op-resume and resumed /op-build share OP Simple runtime: both execute through /op-simple-build; resume toggles resume_mode.
  • Accepted vs effective: opctl accepts a broad parser surface globally; command handlers use only relevant subsets listed above.
