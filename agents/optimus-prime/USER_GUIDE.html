Optimus Prime

Cycle-based orchestrator for automated handoff. Optimus plans, dispatches, tracks, and synchronizes status. Workers execute focused units and return concise summaries.

Tracking: automated-handoff Cycle cadence: 5m Max running workers: 6 Max initialized workers: 10 Per-worker Codex profiles Rate-gated dispatch

What This Agent Does

  • Builds absolute unit-of-work prompts with complete context.
  • Prepares workstation slots before worker launch.
  • Tracks branch lineage so every packet has explicit start_from_branch and start_from_commit.
  • Uses default worker trio: optimus-fullstack-developer, optimus-fullstack-tester, optimus-reviewer.
  • Keeps role/thinking-profile worker threads reusable.
  • Can pin worker slots/roles to different Codex profiles (codex, codex-second, codex-third, etc.).
  • Monitors profile rate snapshots (session JSONL token_count) across profiles, hard-gates low-limit dispatch, and soft-throttles concurrency before hard stop.
  • Owns all Linear updates; workers do not use Linear skill.
  • Runs uninterrupted cycles until mission target is complete.

Concurrency Rules

3max developers
2max testers
1max reviewer
  • Ready tasks 1-3 -> 1 developer.
  • Ready tasks 4-9 -> 2 developers.
  • Ready tasks 10+ -> 3 developers.
  • If only 1 developer is active, run only 1 tester.

Feature Lanes

  • When multiple features are ready, Optimus assigns developers across distinct features first.
  • Developer-to-feature assignment is sticky (avoid mix-and-match reassignment every cycle).
  • If cross-feature parallelism is blocked, Optimus may place multiple developers on one feature temporarily.
  • Same-feature parallel work must stay issue-scoped on separate issue branches.
  • Lane state is tracked in FEATURE_LANES.json and shown in cycle summaries.

Codex Profile Routing

  • Role-based policy example: developers on codex-second, tester/reviewer on codex.
  • Slot-based policy example: dev-1/dev-2 on codex-second, dev-3 on codex-third, test-1/review-1 on codex-fourth.
  • Optimus keeps profile assignment stable per worker thread and passes it via thread-dispatch --codex-home.
  • Optimus also uses thread-dispatch MCP flags to minimize worker MCP access: default --disable-all-mcp, then --enable-only-mcp only when a packet requires it.

Worker MCP Policy

  • Workers never get linear or linear_sse MCP access. Optimus owns all Linear updates.
  • Reviewer: default no MCPs; normally no Playwright or DevTools.
  • Developer: default no MCPs; allow context7 only when docs lookup is explicitly needed.
  • Tester: default no MCPs; allow playwright and/or chrome_devtools only for browser/UI verification packets.
  • MCP enablement is packet-specific and should stay as small as possible.

Rate Gate / Status

  • Runs codex-rate-snapshot on primary and configured worker profiles (default every cycle).
  • Uses profile identity (best effort from auth.json) to derive single-user vs multiple-users mode.
  • Default hard gates: 5h <= 15%, weekly <= 10% (user-overridable).
  • Default soft throttle gate: 5h <= 40% or weekly <= 25% - cap active background workers to 3 (user-overridable).
  • If reset is under 4h, Optimus may sleep until reset and continue; otherwise wind down after active workers finish.
  • In multi-user mode, hard gates and soft throttle are applied per profile so healthy profiles can keep working.

Token Discipline

  • Workers receive minimal, task-complete prompt packets.
  • Workers return short summaries only.
  • No worker advances to next task before phase gates clear.
  • Developer waits for test+review pass before new unit.
  • Tester waits for reviewer decision before next task.

Execution Flow

RESOLVE START ANCHOR + FEATURE LANE + CODEX PROFILE + MCP ALLOWLIST -> RUN RATE SNAPSHOT SKILL + HARD/SOFT RATE CHECKS -> PREPARE SLOT -> DISPATCH DEV -> SLEEP 5m -> DEV DONE (UPDATE LINEAGE + FEATURE LANE) -> DISPATCH TEST -> TEST PASS -> DISPATCH REVIEW -> REVIEW PASS -> LINEAR SYNC -> NEXT UNIT

If a phase fails, Optimus routes the task back to the required phase (dev fix, retest, rereview) until fully accepted.

Branch Conflict Rule

If branch checkout fails because branch is active in another worktree, worker creates a role-suffixed branch and reports mapping.

MYO-23-make-menu-navbar -> MYO-23-make-menu-navbar-test

Stuck Worker Response

  • Detect repeated failed attempts across cycles.
  • Send steering prompt with specific correction.
  • If unresolved, stop worker and block/reassign task.

Identity Safety

  • Optimus writes identity checkpoint reminders.
  • Reloads mission and control rules every few cycles.
  • Prevents context compaction drift in long runs.
